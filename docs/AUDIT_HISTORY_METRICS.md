# Audit history metrics

The history stores 45 measured aggregate trends across five groups. One selected SVG chart is mounted at a time; local, live-source and unknown audit modes remain separate. Percent axes stay at 0–100. Missing measurements break the line. Old six-metric histories migrate to schema 3 with new fields set to null; stored original values remain unchanged. The retention limit remains 120 runs. No network requests or new user/device identifiers are introduced.

## Measurement contract

These values are explicitly scoped measured percentages, not a combined quality grade or certification. Zero requires an observed zero. Missing reports, absent samples, zero denominators, invalid counts and impossible ratios produce `Not measured`. Percentages round to one decimal; nearest-rank p50/p95 values retain their measured milliseconds. A percentage must be read with its scope, which can be sampled screens or automated steps, not all users or products. Run details retain version, outcome, collection/coverage state and executed count.

| Group | Metrics and formula |
| --- | --- |
| Performance | Existing failures, check completion, duration, slowest check, max JS lag and JS animation gap retain their definitions. Wall clock includes pauses. Journey p50/p95 use measured forward work. JS stalls over 100 ms and JS frames over 50 ms divide summed offending samples by summed measured samples, not an average of per-step percentages. These are JavaScript observations, not native dropped-frame measurements. |
| Coverage | Collected checks = unique stored expected performance checks / planned checks. Journey execution = executed journeys / planned journeys. Health execution = executed health checks / planned health checks. Readiness evidence = executed journeys with captured readiness / executed journeys. Responsiveness evidence = executed journeys with both event-loop and frame observations / executed journeys. Verified destinations = classified link results / inventoried links, using the completion engine's gap classification; a verified failure remains a classified result, not a healthy destination. Missing checks, target probe defects and unverified destination counts remain independently visible. |
| Data coverage | Provider fetch success = successful / attempted providers, with valid counts; a successful fetch does not prove exhaustive provider population. Product detail coverage = matched / core products for the same run. History source coverage = (checked days minus distinct source-gap days) / checked days. This is source availability, not verified historical pixels or complete upstream coverage. |
| Task outcomes | Automated task success = invoked actions with explicit completed/nonfunctional-failure-free results, ready evidence and no completion gap / invoked actions. Timing failures may still be functionally successful. Automated task failures count explicit action or functional failures; unknown outcome fields make this percentage unknown. Action p50/p95 cover completed measured semantic actions; route navigation is excluded; Back p95 covers measured returns. Navigation recoveries count returns requiring measured route replacement or anchor reset / measured returns. An ordinary second Back through a tab is not recovery. Runtime errors sum observed journey counters only when all have measurements. These are script outcomes, not participant success or satisfaction. |
| Check results | Check pass rate = passing performance checks / stored performance checks (warnings and skips do not pass). Health pass rate = passing / planned health checks; duplicate or unexpected health identities invalidate the percentage. Data-integrity and data-completeness pass rates = passing / recorded domain checks only when health collection is complete and identities are valid. Timing failure count and historical processing/projection mismatch counts stay separate. |
| Rendering checks | Observed surfaces = (planned minus missing) / planned surfaces, with unique contract evidence; duplicate observations cannot replace missing surfaces. Model, list, visible-content, layout, chart, empty-state and logo pass rates = (checked minus failed/warned/unavailable) / (checked plus missing). Missing required evidence lowers the rate. These existing role checks cover sampled rendered surfaces; they are not WCAG conformance or visual-design certification. |

The original **Check completion** remains comparable with old reports; it is distinct from **Collected checks**, **Journey execution**, and the report's strict boolean coverage status. A local zero-network run can collect every link result while destination verification remains zero. A successful health report does not override missing source identities, unverified upstream population or missing historical rendering evidence.

Legacy completion percentages can survive in public or older reports without the canonical health inventory that contributed to their denominator. Preserve the recorded percentage, but report its denominator as unknown with `missing-denominator`; missing health metadata never establishes a zero health population.

Back timing eligibility requires an executed route round trip or explicit Back timing/outcome evidence. Semantic actions without return evidence are excluded; eligible returns with absent or invalid durations remain missing samples. The percentile uses only measured durations from this population.

Count operands must be nonnegative safe integers before arithmetic, and summed populations must remain safe integers. Fractional timing measurements remain valid. Rejected counts remain available as raw evidence with `inconsistent-counts`; they cannot establish a score or population.

Historical mismatch zeros require recorded processing or chart-projection comparison counts greater than zero. Availability alone does not prove a comparison occurred. Older reports without these counters leave zero mismatches unmeasured; observed positive mismatch counts remain available even when history is partial or unavailable. The comparison counters record actual date-axis, expected-day, product-value, provider-statistic and model-to-chart comparisons performed by the app audit. Reused product-source comparisons retain counts only with the matching cached input evidence. Analysis exposes the mismatch count as its numerator and the comparison count as its sample size with unit `comparison`. These heterogeneous checks neither establish exhaustive upstream coverage nor form independent statistical trials; the total eligible comparison population remains unknown.

## Established measures and limits

Task completion, task time and error rate are established usability measures. This implementation uses their measurable automated analogues with explicit labels. Human ease of use needs participant studies: SUS requires its questionnaire, and SEQ requires task ratings. No participant responses exist in the audit, so no SUS/SEQ score is generated. [Nielsen Norman Group usability metrics](https://www.nngroup.com/articles/usability-metrics/) and [MeasuringU SUS methodology](https://measuringu.com/sus/) describe these separate measurement types.

The check inventory includes performance, stability and responsiveness concerns in [Android's core app quality guidelines](https://developer.android.com/docs/quality-guidelines/core-app-quality). [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) defines a product quality model, not a universal numeric app score; this app does not claim ISO conformance from pass percentages.

[WCAG 2.2](https://www.w3.org/TR/WCAG22/) contains testable accessibility requirements such as contrast and target size. Existing layout/chart probes cannot establish all those criteria. Native JS animation gaps are not browser INP, LCP or CLS. Native rendering/jank, crash-free sessions, contrast/target-size audits, participant satisfaction and web Core Web Vitals require their own collectors and denominators before historical scores can be shown.

## Verification

Focused coverage includes v1 migration, complete v2 validation, impossible score rejection, unknown/zero preservation, weighted sample denominators, functional-versus-timing outcomes, missing plans and links, duplicate health and surface evidence, genuine versus ordinary navigation recovery, display pass arithmetic, a single selected chart, grouping and percentage units. Existing report-storage recovery and retention tests cover the unchanged transaction boundary.


## Per-metric diagnostic analysis

`buildAuditMetricAnalysis` emits a versioned record for every one of the 45 metrics, including unknown metrics. Graph values and report analysis call the same lightweight `auditMetricValues` calculation. Saving aggregate history does not build the full evidence table. The full analysis is available in local raw reports and shared diagnostic envelopes; historical aggregate-only records do not invent raw observations.

Each record contains its source-authored method ID, per-metric method version, exact formula, metric unit, unit of analysis, sample-count unit, numerator/denominator where applicable, eligible/observed/missing/excluded counts, fixed missing-evidence tokens and references into a shared observation table. Observation references retain check positions and IDs, relevant metric fields, and target-probe issue identities. Public exports apply the existing ID/privacy admission. Shared observations avoid repeatedly copying the same checks into dozens of metrics.

Hosted consumers must read `envelope.metricAnalysis` after decoding the complete public envelope. Its nested `envelope.diagnosticLog.metricAnalysis` is `{ "$ref": "$.metricAnalysis" }`: a reference relative to that whole envelope, not an independently embedded analysis. Extracting `diagnosticLog` alone does not produce a standalone analysis document. A consumer exporting that nested object separately must also retain the root analysis or replace the reference with that root value. Calling `fullAuditDiagnosticLog(report, safeCheckId)` without the hosted-only option already embeds full analysis for standalone use.

If the export budget requires omission, both locations instead contain an explicit `status: "omitted"`, `reason: "export-budget"` marker with schema/method versions. Consumers must display that state rather than dereference it or treat it as empty evidence. The retained local report is the regeneration source; the deidentified public log may lack canonical health metadata needed to recreate every metric.

Timing distributions provide sample count, minimum/maximum, nearest-rank p50/p90/p95/p99, median absolute deviation, interquartile range, five worst observations and observed cold/warm/first/repeat strata. These statistics describe the recorded samples. At small sample sizes the upper percentiles can equal the maximum; no artificial tail estimate is interpolated. A distribution of per-check maximum JS lags or frame gaps is explicitly `check-maximum`, not the distribution of individual callbacks. Missing sample evidence remains counted.

Automated task outcomes partition invoked actions into known success, explicit failure and indeterminate evidence. Missing readiness or unknown action results are not successes. Pooled callback metrics expose the observed callback denominator separately from the numbers of contributing and uninstrumented journeys. When callbacks in uninstrumented journeys are unknown, the eligible/missing/excluded callback populations are null, not invented zero counts. Absent optional recovery durations mean no observed replacement/anchor recovery; they do not create fictitious missing samples for normal Back.

No inferential confidence interval is attached to these audit scores. Inventory checks are deterministic observations of a particular suite/catalogue, and repeated action/frame/timer observations share state and are correlated. An ordinary binomial Wilson interval would require a defensible independent-trial sampling model. If independent participant studies are added later, the analysis unit and sampling protocol must be recorded before intervals are introduced. See [NIST's binomial proportion interval guidance](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm); applicability to this audit follows from its deterministic, repeated-state collection design.

Plan sizes, payload product/provider counts, viewport width, font scale and development-build status accompany the analysis. They expose important workload/configuration changes rather than presenting all runs as identically controlled experiments. Device performance improvements still require a comparable real-device audit after release.


## Decisions supported by the current interface

The former **App quality** and **Display quality** headings overstated the measurements. They are now **Check results** and **Rendering checks**. Existing metric IDs and stored values remain unchanged; schema 3 adds per-run method versions; their labels identify the actual check rather than an overall app/design score. A pass percentage is not a weighted assessment of user impact. For example, thousands of intentionally unverified local links can dominate the performance-check pass percentage without thousands of broken interactions, while one failed completeness check can represent many missing products. Check results opens on the actionable timing-failure count, not the broad pass percentage.

For the current retained report, both groups show the numerator, denominator, missing evidence and (for percentages) not-passed count without opening a details panel. Older aggregate-only records have no retained denominator evidence and show it as **Not measured**, never borrowed from a newer run. The labels narrow interpretation:

- Model-count checks establish valid source/model counts; readiness without counts is unavailable evidence.
- List-presence and viewport-count checks establish the sampled list/viewport minimum, not complete offscreen rendering.
- Layout-callback checks establish observed layout callbacks and any supplied geometry/clipping evidence, not independently measured absence of clipping on every widget.
- Chart-contract checks compare model/render counts, layout, empty state and accessible summaries. They do not compare rendered pixels with a reference image.
- Logo-load checks distinguish decoded/fallback/missing assets; empty-state checks compare model emptiness with the rendered empty state.

Check results additionally exposes a mutually exclusive partition of invoked actions: **Ready within timing limits**, **Ready with timing failures**, **Ready with warnings**, **Action failures**, and **Indeterminate**. The first three subdivide the existing gap-free functional-success population by recorded timing/check status. Thus a slow but functionally completed action cannot be mistaken for a responsive success. The counts have the same invoked-action denominator, include repeated scripted visits, and are not user-study percentages. Unknown readiness stays indeterminate. **Human usability**, **Visual design**, and **Pixel correctness** remain explicitly **Not measured** because this audit has no participant study or independent screenshot comparison.

Action-duration method version **2** corrects the eligible sample population: route round trips have forward/Back measurements but no semantic `actionMs`, so they are excluded instead of counted as missing action-duration samples. Explicit semantic actions with absent durations still count as missing. Legacy records with explicit `actionMs` remain eligible. This does not fabricate timings or rewrite historical aggregate values; exports and the evidence panel expose the corrected method version. Schema version remains separate from the method version. Historical schema 1 and 2 runs migrate with method version 1, never retroactively adopting a new population. Graph paths break across method-version boundaries and recorded results show the method version.


The check-group summary uses a lightweight operand/outcome projection, not the full shared-observation table or timing distributions. Its operands are regression-compared with full analysis for every check/rendering metric under valid, missing, invalid, zero and unavailable evidence. Expanded metric details retain the richer analysis. Status-based timely success additionally requires available JavaScript timing observers and a measured forward-work duration; a legacy generic pass without those measurements is only a ready-with-warning result.

`firstReadyFrameMs` in runtime evidence records first required-probe readiness. It is not an independently observed native frame presentation or first-paint timestamp. Journey time and readiness metrics must not be promoted to native rendering or visual-quality measures from that field name.


Rendering method version **2** applies to model-count, list-presence, viewport-count, layout-callback, empty-state and logo-load checks: count-free readiness no longer supplies fabricated counts; required terminal-pending evidence remains adverse; Rates now has explicit visible/empty roles; and earlier adverse model/layout/logo visits survive later success. Chart-contract and unique-surface coverage methods remain version 1 because their population/contract definitions did not change. These per-metric boundaries keep older apparent 100% samples from being joined to corrected series as if they used the same measurement. When scoring admission is unavailable, the UI still exposes known observed/eligible/unavailable role counts separately from missing-role counts; one unavailable observation with zero absent roles is never presented as zero unavailable evidence.
