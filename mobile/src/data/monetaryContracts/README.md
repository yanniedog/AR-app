# Historical savings capability

The optional immutable `executable_v3` namespace routes savings separately from
reserved mortgage and portfolio capabilities. Only requested savings bodies are
downloaded. All descriptors share the publication transfer budget. Frozen v1 and
eligibility v2 contracts retain their existing meanings.

`loadSavingsSelections` requires the actual adopted core/details objects and their
verified identities. Core content is stamped during normalization and checked at
capability boundaries, including after asynchronous downloads. Branded selections
also bind the complete publication, exact product or original selected row,
structured historical authority graph and reviewed asset. Calculations and receipt
exports reject a changed selection or edition.

The producer verifies original historical source members privately. This consumer
verifies approved public structure, canonical identities, source associations,
whole-period field coverage, posting inventory and current publication binding.
It does not download or verify private historical archives on-device. A capture
alone does not prove a continuous rate interval. Supersessions must cover the
actual conflict; adjacent explicit field coverage may compose without gaps.

`calculateSavingsPeriod` builds a single-account v8 ledger using source-owned base
rates, marginal or whole-balance tiers, explicit rounding and complete posting
dates. Posting residue is discarded with an explicit rounding adjustment, matching
the existing engine. Unknown or different residue policies cannot execute.

Account reference, dates, opening balance, account-rate confirmations and scoped
customer answers stay local. Scenario roles cannot be replaced by saved profile
answers. Cleared-only policies require confirmation that all opening funds were
cleared. The customer cannot backdate source coverage or change reviewed rates.
Results concern a historical holding period before tax, with no movements,
opening unposted accrual or withholding. Closure, bonus, intro, offset, linked
accounts, nonzero fees and projected future returns are unsupported here.

The product route exposes this capability lazily, requires an explicit scope, and
invalidates results when local inputs, profile or source edition changes. No
engineering fixture enters product flow and no bank capability is activated by
these changes.

The independent oracle fixture is retained from a separate Python Decimal/calendar
implementation. Tests compare totals, every accrual/posting row, daily basis and
exposed tier contributions, with intended refusal categories. Intermediate daily
cumulative registers are not exposed by the ledger; only their terminal totals are
compared. Actual bridge tests additionally retain exact gzip assets, raw private
inputs, output hashes and separate producer-private completion proof. These are
engineering checks, not bank/source or native acceptance.
